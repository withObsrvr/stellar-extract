# Handoff — go-stellar-sdk v0.6.0 → v0.7.1 (Protocol 28)

**Date:** 2026-08-04
**Status:** Complete, uncommitted. `go build` / `go vet` / `go test` all clean.

## What the release actually contained

**v0.7.0** — Protocol 28 (CAP-0083, CAP-0085). XDR regenerated from
`stellar-xdr@9c9c1459`, the commit stellar-core 28.0.0 pins. Both CAPs are
ungated upstream, so `XDR_FEATURES` is now empty. Also: zero-copy XDR view
extractors for full-history ingestion, `UseUpgradedAuth` on
`SimulateTransactionRequest`, `LedgerCloseTime` on `GetHealthResponse`,
loadtest multi-bundle support, and a captive-core pubnet config change (SP
swapped for Obsrvr).

**v0.7.1** — `ExtractLedgerTxParts` + `EventsFromTxParts`/`FeesFromTxParts`
(the one-ledger-walk API; supersedes and removes the unreleased
`ExtractTxHashes`/`ExtractLedgerEvents` from #5949), and a `stellartoml` domain
validation fix.

Neither release breaks our compile. That was the problem.

## The three Protocol 28 arms that landed in our switches

Protocol 28 added three XDR union arms, and all three hit code this library
owns. Go does not warn about a `switch` that ignores a new arm, so the bump
alone would have compiled, passed CI, and written wrong columns.

| New arm | Site | Symptom of shipping the bump alone |
|---|---|---|
| `SCV_EXECUTABLE_TAG` (`ScValType` 22) | `scval_converter.go` | Contract event topics/data of this type written as `{"error": "unsupported ScVal type: ..."}` into `contract_events_stream_v1` |
| `CONTRACT_EXECUTABLE_EXTERNAL_REF` (`ContractExecutableType` 2) | `soroban.go` contract creations | `wasm_hash` NULL, indistinguishable from a SAC deployment |
| `STELLAR_VALUE_EMPTY_TX_SET` (`StellarValueType` 2) | `ledgers.go` | `node_id` / `signature` NULL — the signature is nested under `proposedValue` on this arm |

Telling detail: the SDK updated **its own** switches for these arms —
`xdr/scval.go`'s `Equals` and `String` both gained cases. Nothing told us to
update ours.

## Pre-existing bug found by the same audit

`transactions.go` read Soroban meta from `TransactionMeta` V3 only. Protocol 23
moved it to V4 (`SorobanTransactionMetaV2`, same `SorobanTransactionMetaExt`).
**`rent_fee_charged` has been NULL for every Soroban transaction since the
Protocol 23 upgrade.** Same failure class, two protocols old. `ledgers.go` and
`soroban.go` already handled both V3 and V4; `transactions.go` was the outlier.

If you have backfilled `transactions_row_v2` since P23, `rent_fee_charged` is
wrong there and needs a re-extract for the affected range.

## Changes

**Dependency**
- `go.mod`: `go-stellar-sdk` v0.6.0 → v0.7.1; `go mod tidy`.

**Correctness**
- `scval_converter.go` — `ScvExecutableTag` case, emitting
  `{"type": "executable_tag", "value": <string>}`.
- `soroban.go` — new `applyExecutable` helper replaces the two duplicated
  `GetWasmHash()` calls. Records the executable kind explicitly and captures the
  external-ref owner and tag.
- `types_soroban.go` — `ContractCreationData` gains `ExecutableType` (`"wasm"` /
  `"stellar_asset"` / `"external_ref"`), `ExternalRefOwner`, `ExternalRefTag`.
  Additive; downstream writers ignore them until their schemas are updated.
- `ledgers.go` — SCP-value signature read extracted into `scpValueSignature`,
  which now handles the empty-tx-set arm.
- `transactions.go` — rent fee read extracted into `sorobanMetaExt`, which now
  handles meta V4.

**Guards (`protocol_coverage_test.go`, new)**

Four exhaustiveness tests. They enumerate the discriminants the SDK declares
valid (via the generated `ValidEnum` / `ArmForSwitch`) and fail when one is
unhandled, with an error message naming the affected column. Verified
non-vacuous: each fails when its fix is reverted.

- `TestConvertScValToJSONHandlesEveryScValType`
- `TestApplyExecutableHandlesEveryContractExecutableType`
- `TestScpValueSignatureHandlesEveryStellarValueType`
- `TestSorobanMetaExtHandlesEveryMetaVersion`

Plus three behaviour tests for the new arms.

**Process**
- `.github/workflows/ci.yml` — added `gofmt` gate, `go mod tidy` drift gate,
  `-race` on tests; toolchain now tracks `go.mod` via `go-version-file` instead
  of the hardcoded `1.26` (go.mod declares 1.25.4, so CI was testing a toolchain
  nobody develops on). New `sdk-pin` job warns when a newer SDK release exists.
- `.github/dependabot.yml` — new. Weekly gomod checks, `github.com/stellar/*`
  grouped.
- `docs/SDK_UPGRADES.md` — new. The upgrade checklist, with the commands for
  diffing `.x` files and listing new enum constants.
- `gofmt -w` applied to four files that were already unformatted on `main`
  (whitespace-only struct-literal alignment) so the new gate starts green.

## Not done — needs a decision

1. **Backfill `rent_fee_charged`** for the P23→now range in
   `transactions_row_v2`. Out of scope for this library; it is a data job.
2. **Downstream schema updates** for the three new `ContractCreationData`
   fields — history loader, streaming ingester, and any nebu processor writing
   `contract_creations_v1`.
3. **Zero-copy view API adoption.** v0.7.0/v0.7.1 added `LedgerTransactionView`
   and `ExtractLedgerTxParts` — on `ledger_58752000` (249 txs) the SDK measures
   ~0.58ms/154 allocs for the walk plus events plus fees, versus ~5.7ms/~95k
   allocs for the parsed path. `ExtractAll` currently runs 16 extractors that
   each walk the parsed `LedgerCloseMeta`, so this is a real opportunity — but
   the APIs are marked **experimental, signatures may still change**, and it is
   a rewrite of every extractor's read path, not a drop-in. Recommend waiting
   for the experimental marker to come off, then shaping it as its own cycle.
4. **`ScvContractInstance` is still lossy.** `ConvertScValToJSON` returns the
   literal string `"complex_contract_instance"` for it. Pre-existing, unrelated
   to this upgrade, but it is a real hole in `contract_events_stream_v1`.
